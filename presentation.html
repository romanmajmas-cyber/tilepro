Плиточные работы под ключ

Веб-приложение с системой заявок, личным кабинетом, панелью администратора и безопасным хранением данных.

Node.js · Express · SQLite · bcrypt · Vanilla JS

Как было — проблема

Первая версия сайта хранила всё в браузере (localStorage). Это работало, но имело серьёзные недостатки.

🔓

Пароли в открытом виде

Любой, кто открыл DevTools → localStorage, видел пароли всех пользователей. Катастрофа.

📱

Данные только на одном устройстве

Заявка, созданная с телефона, не видна на компьютере. Нет синхронизации.

🗑️

Стирание кэша = потеря данных

Очистка браузера или режим инкогнито — и все заявки исчезают навсегда.

🚫

Нет настоящей авторизации

Любой мог «притвориться» админом, поменяв пару значений в localStorage.

Как стало — решение

Полноценный клиент-сервер: фронтенд общается с API, который работает с настоящей базой данных.

  • Настоящий сервер на Node.js + Express — обрабатывает запросы от всех клиентов.
  • SQLite-база — данные хранятся в одном файле, синхронизируются между устройствами.
  • bcrypt-хеширование паролей — даже при утечке БД пароли не читаемы.
  • Токен-сессии — 256-битный токен на 30 дней, хранится в БД.
  • Роли — админ видит все заявки, обычный пользователь — только свои.
  • Полная валидация и защита от SQL-инъекций через prepared statements.

Безопасность

Что именно защищено и как.

🔐

Хеширование паролей

bcrypt с 10 раундами и автосолью. Один и тот же пароль у двух пользователей даёт разные хеши.

🎲

Крипто-токены

crypto.randomBytes(32) = 2256 вариантов. Перебор невозможен.

🛡️

SQL-инъекции

Все запросы через prepared statements с плейсхолдерами ?. Юзер-ввод никогда не попадает в SQL как код.

⏳

TTL сессий

Срок жизни — 30 дней. Просроченные сессии удаляются автоматически каждый час.

🎭

Проверка ролей

Админ-эндпоинты защищены middleware. Пользователь не получит чужие заявки.

🧼

XSS-защита

Все данные из БД экранируются через escapeHtml() перед вставкой в DOM.

Схема базы данных

Три таблицы с связями и индексами для быстрых запросов.

👥 users
  • id — PK
  • name
  • email — UNIQUE
  • password_hash
  • role
  • created_at
📋 requests
  • id — PK
  • user_id — FK → users
  • name, phone, email
  • service, area, address
  • comment
  • status, admin_note
  • created_at
🔑 sessions
  • token — PK
  • user_id — FK → users
  • created_at
  • expires_at

Индексы ускоряют выборки: idx_requests_user, idx_requests_status, idx_sessions_exp. Внешние ключи настроены с ON DELETE CASCADE / SET NULL.
